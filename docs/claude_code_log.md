# Claude Code 활용 기록

README의 "Claude Code 활용 기록" 섹션 원본. Phase마다 **무엇을 요청했고 → Claude Code가 무엇을 만들었고 → 어떻게 검증했고 → 무엇을 고쳤는지**를 남긴다.

---

## Phase 1. 데이터 생성·검증

**요청**: 5개 테이블(departments/employees/workload/skills/staffing_plan) 합성 데이터 생성, 계절성·조직별 특성·스킬 불균형 반영, assert 기반 검증 자동화.

**Claude Code가 만든 것**
- `src/data_gen.py` — seed 고정 생성기, CSV + SQLite 저장
- `src/validate.py` — 7개 무결성 검증 함수 (CLI와 pytest가 같은 함수 사용)
- `tests/test_data.py` — 14개 테스트
- `docs/data_generation.md`

**설계 판단**
- 생성기의 "숨은 정답"(조직별 필요 FTE·성장률)을 테이블에 저장하지 않고, 저장 컬럼을 스키마로 고정해 검증한다. 나중에 예측 모델이 정답을 몰래 참조하는 일을 구조적으로 막기 위함.
- 정원(TO)을 "직전 연말 현원 + 부서 요청분"으로 생성해, 문제 정의("과거 정원·부서 요청에만 의존한 인력계획")를 데이터 자체에 재현했다.

**검증 방법**
1. `python -m src.validate` — 7개 검증 모두 PASS
2. `pytest` — 14 passed
3. **검증 함수 자체를 검증**: 데이터를 일부러 망가뜨려(존재하지 않는 부서 D99, 2026-10 미래 행, 숨은 컬럼 추가, 현원 +1) 검증이 실제로 실패하는지 테스트. "항상 PASS만 나오는 검증"을 피하기 위함.
4. 생성 결과가 의도한 시나리오대로 나왔는지 요약 통계로 확인:
   - 최근 12개월 업무부하(필요 FTE / 현원): AI서비스팀 1.22, 클라우드 1.13 (과부하) / 경영지원 0.87, SI2 0.90 (저활용) — 의도와 일치
   - 월별 업무량 지수: 3·6·9월 1.07~1.09, 1월 0.94 — 분기말 계절성 반영 확인

**발견·수정한 문제**
- `load()`가 테이블명을 f-string으로 SQL에 넣고 있었음 → 테이블명은 파라미터 바인딩이 불가능하므로 스키마 화이트리스트로 제한하도록 수정 (SQL 인젝션 여지 제거).
- Windows 콘솔(cp949)에서 한글 출력이 깨짐 → 파일(CSV는 utf-8-sig, SQLite)은 정상임을 확인. 콘솔 출력 시 `PYTHONIOENCODING=utf-8` 사용.
- 부하율 계산 시 `current_headcount`에 휴직자(8명)가 포함됨을 확인 → Phase 2 KPI에서는 가용 인원(active)으로 계산하기로 결정.

## Phase 2. Module A — 조직 생산성 진단

**요청**: 조직별 현원, 1인당 처리량, 업무부하율, 초과근무 추정치 KPI와 시각화.

**Claude Code가 만든 것**
- `src/kpi.py` — 월별 KPI(`monthly_metrics`)와 최근 12개월 스냅샷(`department_kpis`)
- `tests/test_kpi.py` — 6개 테스트
- `notebooks/analysis.ipynb` Module A 섹션, 차트 3장(`docs/images/a_*.png`)
- `docs/methodology.md` Module A 섹션

**설계 판단**
- 부하율은 월별 비율의 단순 평균이 아니라 **12개월 필요시간 합 / 가용시간 합**으로 계산. 업무량이 많은 분기말 달이 결과에 더 크게 반영되도록.
- 가용인원은 현원이 아니라 **active 인원**(휴직자 제외) 기준 — Phase 1에서 발견한 문제를 반영.
- 1인당 처리량은 조직마다 '1건'의 크기가 달라(2.5h~40h) 조직 간 비교에 쓰지 않는다고 문서에 명시.

**검증 방법**
1. **손으로 계산 가능한 최소 데이터로 공식 검증**: 10명 × 140h = 1,400h, 100건 × 14h = 1,400h → 부하율 정확히 1.0. 120건이면 1.2, 1인당 초과 28h. 휴직 2명이면 1,400 / 1,120 = 1.25. 테스트로 고정.
2. 경계값 테스트: 부하율 1.05는 '적정', 1.06은 '과부하'.
3. 합성 데이터 시나리오 일치 확인: AI·클라우드는 과부하, SI2·경영지원은 저활용으로 분류되는지 테스트.
4. 차트를 이미지로 직접 열어 한글 폰트·라벨 겹침 확인.

**발견·수정한 문제**
- Phase 1 점검 때 AI서비스팀 부하율이 1.22였는데 KPI 모듈에서는 1.37 → 오류인지 확인. Phase 1 점검은 "12개월 필요 FTE / **현재** 현원"이었고, KPI는 **각 월의 그 당시 현원**(AI팀은 1년 전 20명대 초반)과 휴직자 제외를 반영한 값이라 차이가 정상임을 확인. 계산 기준을 methodology.md에 명시.
- 현원·정원·필요 FTE 비교 차트에서 **값이 같은 점이 서로 가려짐**(클라우드: 현원 = 정원 = 38) → 현원을 속이 빈 큰 원으로 바꿔 겹쳐도 보이게 수정.
- 노트북 실행 시 Jupyter 커널이 응답하지 않음(커널 프로세스는 뜨지만 클라이언트 연결 실패, ipykernel 7.x → 6.29.5로 바꿔도 동일). 로컬 환경 문제로 판단하고, 커널 없이 IPython으로 in-process 실행해 출력을 저장하는 방식으로 우회.

## Phase 3. Module B — 업무량 예측 + 적정 TO 산정

**요청**: 월별 업무량 예측(Rolling-origin 검증 1회), FTE 변환, 인력 격차, ±10~20% 민감도.

**Claude Code가 만든 것**
- `src/forecast.py` — 3개 모델(현행 관행 대리 baseline / 추세+계절성 회귀 / XGBoost), Rolling-origin 검증, 12개월 예측
- `src/staffing.py` — 필요 FTE, 권장 정원, FTE·인원 격차, 민감도, 판단 안정성
- `tests/test_forecast.py` — 10개 테스트
- 노트북 Module B 섹션, 차트 3장(`docs/images/b_*.png`), `docs/methodology.md` Module B

**설계 판단**
- 계획서는 "XGBoost 또는 간단한 회귀"였다. 데이터가 조직당 24개월뿐이고 트리 모델은 추세를 외삽하지 못한다는 점 때문에 **회귀를 주 모델**로 하고, XGBoost와 현행 관행을 같은 검증에 넣어 선택 근거를 수치로 남겼다. 모델 비교는 계획서상 생략 대상이었지만, 모델 함수 시그니처를 통일해서 추가 비용이 거의 없었다.
- 정원 산정에는 월별 오차보다 **향후 기간 평균 수준의 오차**가 중요하다고 보고 별도 지표(level_wape, level_err_p90)를 만들었다.
- 민감도는 단순히 숫자를 나열하지 않고, "±10% 안에서 충원/재배치 판단이 뒤집히는가"를 판정해 **확실한 판단과 재검토가 필요한 판단을 구분**했다.

**검증 방법**
1. **노이즈 없는 데이터로 계수 복원**: 정답 계수(a=5, b=0.01, c=0.1, d=−0.05)로 만든 시계열에서 회귀가 계수를 1e-9 오차로 복원하는지.
2. **미래 정보 누출**: 가짜 모델(spy)을 검증 함수에 넣어, 모델이 받는 학습 데이터가 항상 예측 대상보다 과거인지와 정답 컬럼이 예측 입력에 섞이지 않았는지를 모델 함수 안에서 직접 확인.
3. **합성 데이터의 숨은 정답과 비교**: 생성기 파라미터로 계산한 향후 12개월 '진짜' 필요 FTE와 예측값이 8개 조직 모두 5% 이내. 실제로 손계산 대조도 함: AI서비스팀 정답 ≈ 36.9 vs 예측 37.0, 클라우드 49.7 vs 50.0.
4. 손계산 테스트: 100건 × 14h / 140h = 10 FTE, 가용비율 0.8 → 12.5 → 올림 13명.
5. 노트북 해석 문장이 실제 출력과 맞는지 출력값을 직접 대조.

**발견·수정한 문제**
- **부동소수 오차로 정원 1명 과다 산정 가능성**: `0.1*3*40`은 `12.000000000000002`라서 `ceil` 결과가 13이 된다. 소수 6자리 반올림 후 올림하도록 하고 회귀 테스트 추가.
- **노트북 출력 중복**: 모든 표 출력이 두 번씩 저장되고 있었음(Phase 2 커밋 포함). 노트북 실행에 쓰던 IPython 셸이 결과를 stdout에도 출력했기 때문. 실행기를 `exec`/`eval` 기반으로 바꿔 수정하고, 셀별 출력 종류를 출력해 중복이 없는지 확인.
- **차트 문제 3건**: ① 예측 차트의 '가용인원' 라벨이 데이터 선과 겹침 → 패널 제목으로 이동 ② 민감도 차트의 범례 기호(━/─)가 폰트에서 같은 모양으로 그려져 ±10%와 ±20%를 구분할 수 없음 → 실제 범례로 교체 ③ 유니코드 마이너스(−)가 맑은 고딕에 없어 깨짐 경고 → 일반 하이픈으로 교체.
- 노트북 해석에서 정보보안팀(±10% 내 충원 판단 안정)이 빠져 있던 것을 출력과 대조하다 발견해 추가.

## Phase 4. Module C — 스킬 기반 매칭

**요청**: 조직별 스킬 보유 현황 매트릭스, "A조직은 Python 부족, B조직은 여유" 같은 규칙 기반 비교표 (최적화 없이).

**Claude Code가 만든 것**
- `src/skill_match.py` — 공급·수요·격차, 스킬별 비교표, 규칙 기반 재배치 후보, 충원 방식 3분할(재배치/채용/육성)
- `tests/test_skill_match.py` — 9개 테스트
- 노트북 Module C 섹션, 차트 2장(`docs/images/c_*.png`), `docs/methodology.md` Module C

**설계 판단**
- 계획서는 "비교표"까지였지만, Module B가 "몇 명"에 답했으므로 Module C는 **"어떻게 채울지"**(내부 재배치 / 외부 채용 / 육성)까지 답하도록 확장했다. 최적화 없이 6개 규칙으로만 동작하는 그리디 방식이라 계획서의 "규칙 기반" 범위를 지킨다.
- 필요 스킬 비율은 실제 보유 분포를 먼저 확인한 뒤(실무 수준 보유율 조직별 0~68%) 직무 특성에 맞게 정했다. 결과가 그럴듯해 보이도록 맞춘 값이 아님.
- 재배치 규칙에 "빠지면 출발 조직에 새 부족이 생기는 사람은 제외"를 넣어, 한 조직을 채우려고 다른 조직에 구멍을 내는 결과를 막았다.

**검증 방법**
1. 공급 수치를 원본 테이블에서 독립적으로 다시 세어 대조 (active, 숙련도 ≥ 3 조건).
2. 재배치 결과의 제약 조건 전수 확인: 한 사람 1회 배정, 출발 조직 한도·대상 조직 필요 인원 초과 없음, 재배치 인원이 메운다는 스킬을 실제로 숙련도 ≥ 3으로 보유.
3. **재배치 후 출발 조직의 스킬 격차를 처음부터 다시 계산**해, 원래 충족이던 스킬이 부족해지지 않았는지 확인.
4. 같은 입력 → 같은 결과(결정성).

**발견·수정한 문제**
- **결과 해석 중 발견한 누락**: AI서비스팀은 외부 채용 6명인데 ML/DL 부족이 11명이라, 채용만으로는 스킬 격차를 메울 수 없었다. 이를 놓치지 않도록 '육성 필요(최소)' 지표를 추가 → 전사 최소 7명.
- **의미 없는 테스트 교체**: 처음 작성한 육성 인원 테스트가 공식을 테스트 안에서 다시 계산하고 있어 모듈이 틀려도 통과하는 구조였다. 모듈의 실제 출력을 대조하는 테스트로 교체.
- **규칙의 편향을 결과에서 발견**: 클라우드인프라팀(충원 14명)은 내부 재배치가 1명뿐. 원인을 추적하니 우선순위 규칙('메울 수 있는 부족 스킬 수')이 부족 스킬 종류가 많은 AI서비스팀에 유리하게 작동했다. 규칙을 임의로 바꾸면 결과를 원하는 방향으로 맞추는 셈이 되므로, 규칙은 유지하고 **한계로 명시**하고 "최종 배정은 HR·현업이 조직 우선순위를 정해 검토"하도록 노트북·문서에 기재.
- 차트: 히트맵의 '+0' 표기를 '0'으로, 막대 차트의 소수 인원 눈금(2.5명)을 정수 눈금으로 수정.

## Phase 5. AI 설명 기능 (Gemini)

**요청**: Gemini로 "이 조직이 왜 인력 부족으로 분석됐는지" 자연어 요약. 수치는 Python 결과만, LLM은 설명만. 계산 결과와 AI 응답 수치 일치 테스트. **비용이 절대 발생하지 않을 것.**

**Claude Code가 만든 것**
- `src/pipeline.py` — 모든 분석 모듈 실행을 묶은 단일 진입점 (AI 설명·대시보드가 같은 결과 공유)
- `src/ai_explain.py` — `get_department_metrics()`, `explain_gap()`, 수치 검증, 템플릿 대체, 캐시
- `tests/test_ai.py` — 20개 테스트 (실제 API 호출 없음, 가짜 LLM 주입)
- `data/synthetic/ai_cache/explanations.json` — 8개 조직의 실제 Gemini 응답 (전부 수치 검증 통과)

**설계 판단**
- 계획서의 "수치 일치 테스트 3~5개"를 넘어, **런타임에서도 모든 응답을 검증**하도록 했다. 테스트만으로는 실제 운영 중 LLM이 숫자를 지어내는 것을 막을 수 없기 때문.
- 표시 형식(소수 자리, 부호, 단위)을 Python이 확정해서 넘긴다 → LLM이 반올림·변환할 이유를 없앰.
- 비용 방지: 무료 등급 확인 후 호출(사용자가 AI Studio에서 '무료 등급' 확인), 응답 캐시, 도구 미사용, 테스트는 API 무호출.

**검증 방법**
1. 가짜 LLM으로 시나리오별 테스트: 정확한 수치 → 채택 / 지어낸 수치(1.52, 20명) → 거부 / **사실끼리 계산한 수치(39−26=13) → 거부** / API 오류 → 대체 / 캐시 시 재호출 없음.
2. 8개 조직 템플릿 설명 전부 수치 검증 통과.
3. 실제 Gemini 호출 8건 결과를 출력해 직접 읽고 확인 + 커밋된 캐시가 현재 계산 결과와 일치하는지 테스트로 고정.

**발견·수정한 문제**
- **모델 단종(404)**: 기본 모델 `gemini-2.5-flash`가 "신규 사용자에게 더 이상 제공되지 않음"으로 404. 오류 메시지가 권장한 모델(`gemini-3.8-flash`)로 교체. 이때 템플릿 대체가 정상 동작해 앱은 멈추지 않았음을 확인.
- **반복 실패 호출**: 404처럼 다시 해도 같은 오류인데 8개 조직 모두 호출을 시도하고 있었음 → 첫 클라이언트 오류 후 호출 중단.
- **일시적 과부하(503)**: 서버 오류만 대기 후 최대 2회 재시도하도록 추가. 그래도 1건(PMO팀)은 실패 → 템플릿으로 대체된 것 확인 후 해당 조직만 재실행.
- **응답 잘림 + 잘린 응답이 캐시됨 (가장 중요한 버그)**: Gemini 3는 출력 토큰 한도 안에서 내부 추론(thinking)도 하기 때문에 한도 2048에서 응답이 문장 중간에 끊겼다. 잘린 문장 안의 숫자는 모두 맞아서 **수치 검증을 통과했고 캐시에 저장됐다.** 응답 완료 여부(finish_reason = STOP)를 확인해 끊긴 응답은 쓰지 않도록 하고, 한도를 8192로 올리고, 잘린 캐시를 삭제 후 재생성. 회귀 테스트 추가. → 교훈: 수치 검증만으로는 응답 품질을 보장할 수 없고, 응답이 완결됐는지도 별도로 확인해야 한다.
- 템플릿 문장의 조사 오류('37.0로', 'AI서비스팀로')와 '+0명' 표기 → 숫자·이름 뒤 조사를 쓰지 않는 문장으로 바꾸고 0은 부호 없이 표기.

## Phase 6. Streamlit 대시보드

**요청**: 2개 화면 — ① 조직 현황(부서별 KPI, 업무부하율, 현원/정원) ② 적정 TO 산정(예측 업무량, 필요 FTE, 인력 격차, 민감도).

**Claude Code가 만든 것**
- `app/dashboard.py` — 2개 탭. ②에는 예측 오차 슬라이더(±20%에서 권장 정원 실시간 재계산), 조직 상세(실적·예측 차트, AI 설명, 스킬 기반 충원 방식) 포함
- `tests/test_dashboard.py` — Streamlit `AppTest`로 브라우저 없이 앱 실행하는 스모크 테스트 4개

**설계 판단**
- 대시보드는 계산하지 않고 `pipeline.run_all()` 결과만 표시 → 노트북·AI 설명·대시보드의 수치가 항상 같다.
- AI 설명은 **API를 호출하지 않고** 수치 검증을 통과한 저장 응답만 표시 → 누가 열어도 비용·한도 소모 없음.
- Plotly를 써서 모든 차트에 마우스오버 상세 정보(필요 FTE, 가용인원, 판단 안정성 등) 제공.

**검증 방법**
1. 브라우저(앱 내장 브라우저)에서 실제로 실행해 두 탭의 텍스트·차트 수 확인, 서버 로그·콘솔 오류 확인.
2. 슬라이더를 +10%로 움직여 8개 조직의 인원 격차가 노트북 민감도 표(+10% 열)와 정확히 일치하는지 대조.
3. 재배치 검토 조직(경영지원팀)을 선택해 '재배치 후보' 분기가 동작하는지 확인.
4. 위 확인 사항을 `AppTest` 자동 테스트로 고정 (카드 수치 = 분석 모듈 계산값, 슬라이더 연동, 검증된 AI 설명 표시).

**발견·수정한 문제**
- **슬라이더와 상단 카드 불일치**: 슬라이더를 +10%로 움직이면 차트는 바뀌는데 위의 카드(권장 정원 합계, 충원 필요 +41명)는 그대로 → 한 화면에서 두 숫자가 모순. 슬라이더를 카드 위로 옮기고 카드도 같은 가정으로 계산(+10%: 충원 +65명, 재배치 −2명). 슬라이더 값이 0이 아닐 때는 "아래 AI 설명·스킬 매칭은 0% 기준"이라는 안내 표시. 회귀 테스트 추가(옛 코드에서는 +41 ≠ +65로 실패).
- **폐기 예정 API 사용**: 서버 로그에 `use_container_width`가 제거 예정 시한(2025-12-31)을 넘겼다는 경고 → `width="stretch"`로 교체 후 경고 사라짐 확인.
- 브라우저 콘솔 오류 1건은 앱이 아닌 외부 주입 스크립트에서 발생한 것으로 확인(무시).
- 첫 로딩 약 20초(검증용 백테스트에서 XGBoost를 12회 학습). `st.cache_resource`로 이후 즉시 표시.
