# 방법론

> 모든 데이터는 합성 데이터입니다 ([data_generation.md](data_generation.md)). 아래 가정값은 `src/config.py`, `src/kpi.py`에 상수로 정의되어 있습니다.

## 공통 가정

| 항목 | 값 | 근거 |
|---|---|---|
| 1인당 월 가용시간 | 140h | 월 소정근로 약 165h − 교육·회의·휴가·행정 등 비직접업무 약 15% |
| 휴직 비율 | 기준시점 비율을 과거에도 적용 | 휴직 이력 데이터가 없어 단순화 |
| 집계 기간 | 최근 12개월 | 분기말 계절성 1주기를 모두 포함 |

## Module A. 조직 생산성 진단 (`src/kpi.py`)

조직 d, 월 t에 대해:

```
필요시간        = task_count × standard_hours
가용인원        = actual_headcount × active_ratio
가용시간        = 가용인원 × 140h
업무부하율      = 필요시간 / 가용시간
1인당 처리량    = task_count / 가용인원
초과근무 추정   = max(0, 필요시간 − 가용시간) / 가용인원
```

**스냅샷 KPI** (최근 12개월 집계)

| KPI | 계산 | 비고 |
|---|---|---|
| 부하율 | Σ필요시간 / Σ가용시간 | 월별 비율의 평균이 아닌 합계의 비율 — 업무량이 많은 달에 가중 |
| 최대 월부하율 | max(월별 부하율) | 분기말 피크 확인용 |
| 과부하 개월수 | 부하율 > 1.0인 달 수 | |
| 1인당 월 초과(h) | 월별 초과근무 추정의 평균 | 부족분 전부를 초과근무로 메운다고 가정한 **상한** |
| 업무량 YoY | 최근 12개월 Σ필요시간 / 직전 12개월 − 1 | |
| 상태 | 부하율 > 1.05 과부하 / < 0.95 저활용 / 그 외 적정 | ±5%는 측정 오차·일시 변동을 감안한 허용폭 |

**주의**: 업무 1건의 의미가 조직마다 다르므로(운영 티켓 2.5h vs AI 과제 40h) *1인당 처리량은 조직 간 비교에 쓰지 않고* 조직 내 추이 확인에만 쓴다. 조직 간 비교는 시간 단위로 환산된 부하율로 한다.

**한계**: 표준처리시간이 고정이라 숙련도·자동화에 따른 생산성 변화를 반영하지 못한다. 실제 조직에서는 표준시간 자체를 주기적으로 재측정해야 한다.

## Module B. 업무량 예측 + 적정 TO 산정 (`src/forecast.py`, `src/staffing.py`)

### B-1. 예측 모델

| 모델 | 식 | 역할 |
|---|---|---|
| baseline_mean | 최근 12개월 평균 | 현행 관행("작년 수준 유지")의 대리 지표 |
| **seasonal_trend** | 조직별 `log(task_count) = a + b·t + c·분기말 + d·1월` (최소제곱) | **주 모델** |
| xgboost | 조직 one-hot·t·월·분기말 → log(task_count) | 비교용 |

**주 모델 선택 이유**
- 조직당 24개월(관측 24개)뿐이라, 파라미터 4개짜리 모델이 과적합 위험이 적다.
- 계수가 그대로 "월 성장률", "분기말 증가폭"이라서 현업에 근거를 설명할 수 있다.
- 트리 기반 모델(XGBoost)은 학습 범위 밖의 t로 **외삽하지 못해** 성장 조직의 업무량을 과소 예측한다. 검증에서 실제로 확인됐다(AI서비스팀 WAPE: 회귀 3.3% vs XGBoost 6.4%).
- log 변환: 성장·계절 효과를 비율(%)로 다루기 위함. 역변환 시 생기는 편향(exp(σ²/2) ≈ 0.1%)은 무시할 수준이라 보정하지 않았다.

### B-2. Rolling-origin 검증

- 기준점 o = 11..22 (학습 12~23개월), 각 기준점에서 o+1..o+6개월 예측 → 기준점 12개
- 기준점 이후 데이터는 학습에 쓰지 않는다 (`rolling_origin` 내부 assert + 테스트에서 모델 함수 안에서 재확인)
- 지표
  - **monthly_wape** = Σ|실제−예측| / Σ실제 (월 단위)
  - **level_wape** = 예측 구간(최대 6개월) *평균 수준*의 오차 — 정원은 평균 수준으로 산정하므로 이 값이 실제로 중요
  - **level_err_p90** = 평균 수준 오차의 90분위 — 민감도 범위 설정 근거

| 모델 | monthly_wape | level_wape | level_err_p90 | bias |
|---|---|---|---|---|
| seasonal_trend | 3.5% | 2.4% | 4.6% | +0.7% |
| xgboost | 4.6% | 3.6% | 6.1% | +0.1% |
| baseline_mean | 6.6% | 5.0% | 14.0% | −0.4% |

주 모델의 월 오차 3.5%는 데이터 생성 시 넣은 월 노이즈(σ=4%, 기대 절대오차 ≈ 3.2%)에 근접 — 남은 오차는 대부분 예측 불가능한 변동이다.

**합성 데이터라서 가능한 추가 검증**: 생성기에 숨겨 둔 '진짜' 필요 FTE와 예측 필요 FTE를 비교해 8개 조직 모두 5% 이내임을 테스트로 확인 (`test_forecast_close_to_generator_ground_truth`). 실제 데이터에서는 이 검증이 불가능하다.

### B-3. 적정 정원 산정

```
필요 FTE    = 예측 task_count × standard_hours / 140h     (향후 12개월 평균)
권장 정원   = ceil(필요 FTE / active_ratio)
FTE 격차    = 필요 FTE − 가용인원
인원 격차   = 권장 정원 − 현원          (+ 충원 필요 / − 재배치 검토)
정원 조정폭 = 권장 정원 − 현재 승인 정원
```

- **가용비율로 나누는 이유**: 정원·현원에는 휴직자가 포함되지만 업무는 가용인원만 처리한다.
- **올림(ceil)**: 정원은 정수. 인력 부족의 비용(과부하, 이탈)이 여유 1명의 비용보다 크다고 판단. 부동소수 오차(예: 12.000000000000002 → 13)를 막기 위해 소수 6자리 반올림 후 올림.
- **평균 기준**: 권장 정원은 12개월 평균 업무량 기준. 분기말 피크(`peak_fte`)는 정원이 아니라 일시 지원·조직 간 협업으로 대응한다고 가정했다.
- "재배치 검토"는 감원이 아니라 Module C의 스킬 기반 재배치 후보라는 의미로 사용한다.

### B-4. 민감도

실제 업무량 = 예측 × (1+e), e ∈ {−20%, −10%, 0, +10%, +20%}로 인원 격차를 다시 계산한다.
- 검증된 오차는 6개월 앞 기준 90분위 4.6%. 12개월 앞은 데이터가 부족해 검증하지 못했으므로 보수적으로 **±10%를 판단 기준 범위**로 둔다.
- **판단 안정성**: ±10% 범위 안에서 인원 격차의 부호(충원/유지/재배치)가 바뀌지 않으면 '안정', 바뀌면 '재검토 필요'.

### 한계

- 검증 가능한 예측 거리는 6개월. 12개월 예측의 정확도는 직접 검증하지 못했다.
- 추세가 직선(log 기준)으로 계속된다고 가정한다. 신규 사업 수주·조직 개편 같은 구조 변화는 반영하지 못한다.
- 업무량이 늘면 표준시간 학습효과로 1건당 시간이 줄 수 있으나 반영하지 않았다.

## Module C. 스킬 기반 매칭 (`src/skill_match.py`)

최적화(선형계획법 등) 없이, 사람이 검토할 수 있는 규칙만 사용한다.

```
공급  supply[d, s] = 조직 d의 가용 인원 중 스킬 s 숙련도 ≥ 3(실무 가능)
수요  demand[d, s] = ceil(필요 비율[d, s] × 권장 정원[d])     ← Module B 결과 사용
격차  = 공급 − 수요   (− 부족 / + 여유)
```

- **필요 비율**(`SKILL_REQUIREMENTS`)은 직무 특성에 근거한 가정값이다. 예: AI서비스팀은 권장 정원의 70%가 Python, 40%가 ML/DL을 실무 수준으로 보유해야 한다. 실제 적용 시 직무기술서·현업 인터뷰로 정해야 한다. 계획서의 5개 테이블 구조를 유지하기 위해 별도 테이블이 아닌 코드 설정값으로 두었다.
- 수요를 **권장 정원** 기준으로 잡은 이유: 충원 후의 조직이 갖춰야 할 스킬 구성을 보기 위해서. 따라서 부족분에는 "새로 뽑을 사람이 가져야 할 스킬"이 포함된다.

### 재배치 규칙 (그리디, 결정적)

1. 후보: 인원 격차 < 0인 조직(재배치 검토)의 가용 인원
2. 대상 조직의 부족 스킬을 실무 수준으로 1개 이상 보유
3. 우선순위: 메울 수 있는 부족 스킬 수 ↓ → 해당 스킬 숙련도 합 ↓ → 사번 ↑
4. 출발 조직의 재배치 가능 인원(|인원 격차|), 대상 조직의 충원 필요 인원 초과 금지
5. 대상 조직에서 그 사람이 메울 부족 스킬이 이미 다 채워졌으면 배정하지 않음
6. **그 사람이 빠지면 출발 조직에 새 스킬 부족이 생기는 경우 배정하지 않음**

### 충원 방식 3분할

```
외부 채용     = 충원 필요 − 내부 재배치
육성 필요     = max(0, 재배치 후 남은 스킬 부족 최대치 − 외부 채용)
```
외부 채용 인원 전원이 부족 스킬을 갖춘다고 가정해도 남는 부족분은 기존 인력 육성(업스킬링)으로만 메울 수 있다 → **최소** 육성 인원.

### 한계

- 우선순위가 '메울 수 있는 부족 스킬 수'이므로, 부족 스킬 종류가 많은 조직이 후보를 먼저 가져간다. 한 가지 핵심 스킬이 크게 부족한 조직(예: 클라우드)에 불리할 수 있다. 결과는 **검토 대상 후보 목록**이며 확정안이 아니다.
- 스킬 보유 여부·숙련도만 본다. 본인 희망, 경력 경로, 성과, 업무 인계, 직급 등은 반영하지 않는다.
- 스킬 숙련도는 자기 신고/평가 데이터라고 가정했으며, 측정 오차를 고려하지 않았다.
